## Overview

Alembic is a database migration tool for SQLAlchemy that allows you to:

- Track database schema changes over time
- Apply incremental updates to your database
- Rollback changes when needed
- Synchronize database schema across different environments

Our project is configured with:

- **Database**: PostgreSQL
- **Script Location**: `alembic/` directory
- **Models**: Located in `app/db/models/`
- **Configuration**: Environment-based configuration using `app/core/config.py`

## Prerequisites

Before working with migrations, ensure you have:

1. **Database Running**: Start your PostgreSQL database

   ```bash
   docker compose up -d
   ```

2. **Python Environment**: Activate your virtual environment (if using one)

   ```bash
   # If using poetry
   poetry shell

   # If using venv
   source venv/bin/activate
   ```

3. **Dependencies Installed**: Ensure all dependencies are installed
   ```bash
   poetry install
   # or
   pip install -r requirements.txt
   ```

## Initial Setup

### 1. Verify Alembic Configuration

Check that your `alembic.ini` is properly configured:

```bash
cat alembic.ini
```

### 2. Verify Database Connection

Test that Alembic can connect to your database:

```bash
alembic current
```

### 3. Create Your First Migration

Since your `alembic/versions/` directory is empty, you'll need to create your initial migration:

```bash
alembic revision --autogenerate -m "Initial migration"
```

This will:

- Analyze your current models in `app/db/models/`
- Generate a migration script
- Place it in `alembic/versions/`

### 4. Apply the Migration

```bash
alembic upgrade head
```

## Basic Migration Workflow

### 1. Make Model Changes

Edit your models in `app/db/models/`. For example, adding a new field to the User model:

```python
# app/db/models/user.py
class User(Base):
    __tablename__ = "users"

    id: Mapped[int] = mapped_column(Integer, primary_key=True)
    username: Mapped[str] = mapped_column(String(30), unique=True, nullable=False)
    hashed_password: Mapped[str] = mapped_column(String(128), nullable=False)
    is_active: Mapped[bool] = mapped_column(default=True)
    email: Mapped[str] = mapped_column(String(255), unique=True, nullable=False)  # New field
    # ... rest of your model
```

### 2. Generate Migration

```bash
docker compose exec web poetry run alembic revision --autogenerate -m "Add email field to users"
```

### 3. Review Generated Migration

Always review the generated migration file in `alembic/versions/` before applying:

```python
# Example migration file content
"""Add email field to users

Revision ID: abc123def456
Revises: previous_revision
Create Date: 2025-08-16 10:30:00.123456

"""
from alembic import op
import sqlalchemy as sa

def upgrade() -> None:
    # ### commands auto generated by Alembic - please adjust! ###
    op.add_column('users', sa.Column('email', sa.String(length=255), nullable=False))
    op.create_unique_constraint(None, 'users', ['email'])
    # ### end Alembic commands ###

def downgrade() -> None:
    # ### commands auto generated by Alembic - please adjust! ###
    op.drop_constraint(None, 'users', type_='unique')
    op.drop_column('users', 'email')
    # ### end Alembic commands ###
```

### 4. Apply Migration

```bash
docker compose exec web poetry run alembic upgrade head
```

## Common Migration Commands

### Check Current Migration Status

```bash
# Show current revision
alembic current

# Show migration history
alembic history

# Show pending migrations
alembic history --verbose
```

### Creating Migrations

```bash
# Auto-generate migration from model changes
alembic revision --autogenerate -m "Description of changes"

# Create empty migration file (for manual migrations)
alembic revision -m "Manual migration description"
```

### Applying Migrations

```bash
# Apply all pending migrations
alembic upgrade head

# Apply specific number of migrations
alembic upgrade +2

# Apply to specific revision
alembic upgrade abc123def456
```

### Rolling Back Migrations

```bash
# Rollback one migration
alembic downgrade -1

# Rollback to specific revision
alembic downgrade abc123def456

# Rollback to base (empty database)
alembic downgrade base
```

### Database Information

```bash
# Show SQL that would be executed (without running it)
alembic upgrade head --sql

# Show current database state
alembic show current

# Show specific revision details
alembic show abc123def456
```

## Advanced Migration Scenarios

### 1. Data Migrations

For migrations that require data transformation, create a manual migration:

```python
# Example: Populate new email field with username + domain
def upgrade() -> None:
    # Add the column first
    op.add_column('users', sa.Column('email', sa.String(length=255), nullable=True))

    # Update existing data
    connection = op.get_bind()
    connection.execute(
        sa.text("UPDATE users SET email = username || '@example.com' WHERE email IS NULL")
    )

    # Make the column non-nullable
    op.alter_column('users', 'email', nullable=False)
    op.create_unique_constraint('uq_users_email', 'users', ['email'])

def downgrade() -> None:
    op.drop_constraint('uq_users_email', 'users', type_='unique')
    op.drop_column('users', 'email')
```

### 2. Complex Schema Changes

For complex changes, you might need to:

```python
def upgrade() -> None:
    # Create new table
    op.create_table(
        'user_settings',
        sa.Column('id', sa.Integer(), nullable=False),
        sa.Column('user_id', sa.Integer(), nullable=False),
        sa.Column('setting_key', sa.String(50), nullable=False),
        sa.Column('setting_value', sa.Text(), nullable=True),
        sa.PrimaryKeyConstraint('id'),
        sa.ForeignKeyConstraint(['user_id'], ['users.id'])
    )

    # Migrate data from old columns to new table
    connection = op.get_bind()
    # ... data migration logic

    # Drop old columns
    op.drop_column('users', 'old_setting_column')
```

### 3. Index Management

```python
def upgrade() -> None:
    # Create indexes
    op.create_index('idx_users_email', 'users', ['email'])
    op.create_index('idx_users_created_at', 'users', ['created_at'])

def downgrade() -> None:
    op.drop_index('idx_users_created_at', table_name='users')
    op.drop_index('idx_users_email', table_name='users')
```

### 4. Working with Multiple Environments

For different environments (development, staging, production):

```bash
# Development
alembic -c alembic.ini upgrade head

# Production (with different config)
alembic -c alembic.prod.ini upgrade head
```

## Best Practices

### 1. Migration Naming

Use descriptive names for your migrations:

```bash
# Good
alembic revision --autogenerate -m "Add user email verification fields"
alembic revision --autogenerate -m "Create user_profiles table"
alembic revision --autogenerate -m "Add index on user.created_at"

# Bad
alembic revision --autogenerate -m "Update user"
alembic revision --autogenerate -m "Fix"
```

### 2. Review Before Applying

Always review generated migrations:

- Check that the changes match your expectations
- Verify data migrations won't cause data loss
- Ensure downgrade functions work correctly

### 3. Test Migrations

Test your migrations in a development environment:

```bash
# Apply migration
alembic upgrade head

# Test your application
python -m pytest

# Test rollback
alembic downgrade -1

# Test forward migration again
alembic upgrade head
```

### 4. Backup Before Production

Always backup your production database before applying migrations:

```bash
# PostgreSQL backup example
pg_dump -h localhost -U liberoo_user liberoo_db > backup_$(date +%Y%m%d_%H%M%S).sql
```

### 5. Handle Nullable Constraints Carefully

When adding non-nullable columns to existing tables:

```python
def upgrade() -> None:
    # Add as nullable first
    op.add_column('users', sa.Column('email', sa.String(255), nullable=True))

    # Populate with data
    connection = op.get_bind()
    connection.execute(
        sa.text("UPDATE users SET email = username || '@temp.com' WHERE email IS NULL")
    )

    # Make non-nullable
    op.alter_column('users', 'email', nullable=False)
```

### 6. Version Control

Always commit your migration files to version control:

```bash
git add alembic/versions/
git commit -m "Add migration: Add user email verification fields"
```

## Troubleshooting

### 1. Empty Migration Files (Migration Generated but Contains Only `pass`)

**Problem**: Migration file is generated successfully but contains empty `upgrade()` and `downgrade()` functions with only `pass` statements.

**Cause**: Alembic cannot detect your models because they're not properly imported.

**Solution**: Ensure all models are imported in your project structure:

1. **Check `app/db/models/__init__.py`** - Should import all models:

   ```python
   # Import all models so they are registered with SQLAlchemy Base metadata
   from .user import User, Profile
   from .accessibility import Accessibility
   from .country import Country
   from .language import Language

   __all__ = ["User", "Profile", "Accessibility", "Country", "Language"]
   ```

2. **Check `app/db/base.py`** - Should import all models:

   ```python
   # Add this after the Base class definition
   from app.db.models import *  # noqa: F401, F403
   ```

3. **Regenerate migration**:

   ```bash
   # Remove the empty migration file
   rm alembic/versions/[empty_migration_file].py

   # Create new migration with proper model detection
   docker compose exec web poetry run alembic revision --autogenerate -m "Description"
   ```

### 2. "nodename nor servname provided, or not known" (Connection Error)

**Problem**: `psycopg.OperationalError: [Errno 8] nodename nor servname provided, or not known`

**Cause**: Running Alembic from host machine when database is in Docker container.

**Solution**: Always run Alembic commands inside the Docker container:

```bash
# ✅ Correct
docker compose exec web poetry run alembic [command]

# ❌ Wrong - causes connection error
poetry run alembic [command]
```

### 3. "Target database is not up to date"

This usually means your database is ahead of your migration files:

```bash
# Check current state
docker compose exec web poetry run alembic current

# Stamp the database with a specific revision
docker compose exec web poetry run alembic stamp head
```

### 4. "Can't locate revision identified by 'abc123'"

Migration file might be missing or corrupted:

```bash
# Check what files exist
ls alembic/versions/

# Check alembic history
docker compose exec web poetry run alembic history
```

### 5. Database Connection Issues

Verify your database settings in `app/core/config.py`:

```python
# Check database URL format (run inside container)
docker compose exec web poetry run python -c "from app.core.config import settings; print(settings.database_url)"
```

Test connection manually:

```bash
# Test PostgreSQL connection
docker compose exec db psql -U liberoo_user -d liberoo_db
```

### 6. Import Errors

If you get import errors when running migrations:

```bash
# Ensure your app is in Python path
export PYTHONPATH="${PYTHONPATH}:$(pwd)"
alembic upgrade head
```

### 5. Merge Conflicts in Migration Files

When multiple developers create migrations:

```bash
# Create a merge migration
alembic merge heads -m "Merge migrations"
```

### 6. Rolling Back Failed Migrations

If a migration fails partway through:

```bash
# Check current state
alembic current

# Force stamp to previous revision
alembic stamp abc123def456

# Fix the migration file
# Then try again
alembic upgrade head
```
